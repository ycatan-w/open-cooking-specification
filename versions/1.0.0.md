# Open Cooking Specification (OCS)

Version 1.0.0

---

# Abstract

The Open Cooking Specification (OCS) defines an open, structured, and extensible format for representing culinary knowledge.

The specification was designed to make recipes understandable by both humans and software systems while remaining simple enough to be authored manually.

OCS can be used for:

- recipe applications
- cooking websites
- educational material
- personal recipe collections
- AI-assisted cooking systems
- culinary archives
- structured publishing
- interoperability between cooking tools

The specification focuses on practical recipe representation rather than professional culinary certification or nutritional regulation.

---

# Status of This Document

This document defines version `1.0.0` of the Open Cooking Specification.

The specification is intended to remain:

- implementation independent
- human readable
- machine processable
- extensible
- backward compatible within minor versions

This specification uses normative terminology as defined in [RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119).

# 1. Introduction

Cooking information exists in many incompatible forms:

- handwritten recipes
- websites
- mobile applications
- books
- cooking videos
- note-taking systems
- AI prompts

Most recipe formats are either:

- too informal for reliable processing
- too rigid for practical cooking
- tied to a specific application
- difficult to extend

The Open Cooking Specification attempts to solve this problem by defining a portable and extensible structure for recipes and culinary knowledge.

The specification treats recipes as structured knowledge rather than plain text.

This allows:

- reuse of ingredients and techniques
- validation of recipe structure
- machine interpretation
- interoperability across systems
- progressive enhancement through extensions

At the same time, OCS intentionally remains readable and writable by humans.

A cook should be able to understand an OCS document without being a software engineer.

Likewise, a developer should be able to implement an OCS-compatible parser or application without culinary expertise.

---

# 2. Design Philosophy

OCS is built around several core principles.

## 2.1 Human Readability First

Recipes are fundamentally human instructions.

Even when represented structurally, recipes should remain understandable without specialized tooling.

The specification therefore prioritizes:

- readable field names
- explicit structures
- minimal syntactic complexity
- compatibility with YAML and JSON

## 2.2 Structured But Flexible

Cooking practices vary significantly across:

- cultures
- households
- professional kitchens
- dietary traditions
- educational contexts

The specification intentionally avoids excessive rigidity.

Instead of attempting to normalize every culinary concept globally, OCS defines:

- a stable core model
- recommended enumerations
- extension mechanisms

This allows ecosystems to adapt the format without fragmenting interoperability.

## 2.3 Reusability

Recipes often reuse:

- stocks
- sauces
- doughs
- spice blends
- techniques
- equipment

OCS therefore supports reference-based composition.

Reusable objects can be defined once and referenced throughout a document.

## 2.4 Implementation Independence

OCS does not assume:

- a database model
- a programming language
- a frontend framework
- a rendering engine
- a storage platform

The specification defines only the data representation.

Applications remain free to implement their own:

- interfaces
- validation layers
- workflows
- rendering systems

## 2.5 Progressive Complexity

Simple recipes should remain simple.

A minimal OCS document can contain only:

- a recipe name
- ingredients
- procedure steps

More advanced systems may progressively add:

- reusable references
- annotations
- metadata
- equipment
- techniques
- extensions

---

# 3. Goals and Non-Goals

## 3.1 Goals

The Open Cooking Specification aims to provide:

### Structured Recipe Representation

Recipes should be represented as structured data rather than unstructured text.

### Interoperability

Recipes should move between systems without requiring custom conversion logic.

### Extensibility

Applications should be able to introduce additional metadata without modifying the core specification.

### Human Accessibility

Non-technical users should still be able to read and author documents.

### Machine Processability

Applications should be able to:

- validate recipes
- index ingredients
- analyze procedures
- build shopping lists
- generate cooking timelines
- integrate AI systems

### Long-Term Stability

Documents should remain readable across future versions whenever possible.

---

## 3.2 Non-Goals

OCS intentionally does not attempt to define:

### Professional Culinary Standards

The specification does not certify culinary correctness.

### Nutritional Regulation

Nutrition systems are intentionally outside the core model.

### Food Safety Compliance

Regional food regulations are not standardized by OCS.

### Canonical Culinary Taxonomies

Ingredient categories and classifications remain intentionally flexible.

### Rendering Rules

The specification does not dictate how recipes must appear visually.

### Workflow Systems

Kitchen workflows and restaurant management systems are outside scope.

---

# 4. Scope

The specification defines:

- document structure
- reusable object models
- references
- extension mechanisms
- compatibility rules
- validation expectations

The specification does not define:

- databases
- APIs
- authentication
- synchronization systems
- storage engines
- rendering standards

---

# 5. Terminology and Conventions

## 5.1 Normative Language

The keywords:

- MUST
- MUST NOT
- REQUIRED
- SHOULD
- SHOULD NOT
- MAY

are interpreted as described in [RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119).

Normative statements define mandatory behavior for compliant implementations.

Informative text exists to explain intent and provide guidance.

---

## 5.2 Primitive Types

The following primitive types are used throughout this specification.

| Type               | Description                                                                      |
| ------------------ | -------------------------------------------------------------------------------- |
| `string`           | UTF-8 encoded text                                                               |
| `integer`          | Whole numeric value                                                              |
| `number`           | Numeric value, including decimals                                                |
| `boolean`          | True or false value                                                              |
| `duration`         | [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) duration string               |
| `link`             | URI-formatted string ([RFC 3986](https://datatracker.ietf.org/doc/html/rfc3986)) |
| [`T`]              | Array containing values of type T                                                |
| Map[`string`, `T`] | Object whose keys are strings and values are type T                              |

---

## 5.3 Supported Serialization Formats

OCS is serialization agnostic.

However, the specification is primarily designed around:

- [YAML 1.2](https://yaml.org/spec/1.2.2/)
- [JSON](https://www.json.org/json-en.html) ([RFC 8259](https://datatracker.ietf.org/doc/html/rfc8259))

YAML examples are used throughout this document because they are generally easier for humans to read and write.

---

## 5.4 Unknown Fields

Unless explicitly prohibited:

- unknown fields SHOULD be ignored
- unknown extensions MUST be ignored

This rule enables forward compatibility.

---

## 5.5 Extension Prefixes

Extension fields MUST begin with:

```yaml
x-
```

Examples:

```yaml
x-nutrition:
x-cost:
x-ai-hints:
```

---

## 5.6 References

Reusable objects MAY be referenced using:

```yaml
$ref: "#/ingredients/basic-stock"
```

References allow modular and reusable recipe definitions.

# 6. Document Structure

An Open Cooking Document is the root container of the specification.

A document MAY contain:

- reusable ingredients
- reusable techniques
- reusable equipment
- one or more recipes
- extension metadata

A valid document MUST contain:

- `openCooking`
- `info`
- at least one recipe

---

## 6.1 Root Document Responsibilities

The root document acts as:

- the namespace for references
- the organizational container
- the extension boundary
- the version declaration point

This design keeps documents self-contained and portable.

---

## 6.2 Minimal Document Example

```yaml
openCooking: 1.0.0

info:
  title: Simple Recipes

recipes:
  scrambled-eggs:
    name: Scrambled Eggs

    ingredients:
      - name: Eggs
        quantity: 4
        unit: unit

      - name: Butter
        quantity: 20
        unit: g

    steps:
      - instruction: Crack eggs into a bowl and whisk.

      - instruction: Melt butter in a pan over medium heat.

      - instruction: Cook eggs while stirring continuously.
```

This represents the smallest practically useful compliant structure.

---

## 6.3 Reusable Collections

Documents MAY define reusable collections such as:

- ingredients
- techniques
- equipment

These collections are intended to reduce duplication.

Example:

```yaml
ingredients:
  chicken-stock:
    name: Chicken Stock
```

A recipe may later reference that object instead of redefining it.

---

# 7. References and Reusability

References are one of the central concepts of OCS.

They allow recipes to reuse existing definitions.

## 7.1 Why References Exist

Many recipes contain reusable components:

- sauces
- spice blends
- doughs
- marinades
- stocks
- equipment
- techniques

Without references, these definitions would need to be duplicated repeatedly.

References improve:

- maintainability
- consistency
- modularity
- reuse

---

## 7.2 Local References

Local references target another object inside the same document.

Examples:

```yaml
#/recipes/basic-stock
#/ingredients/mayonnaise
#/equipment/whisk
```

---

## 7.3 Reference Resolution

Implementations SHOULD resolve valid references.

Invalid references SHOULD be treated as errors.

Applications MAY:

- validate references during parsing
- resolve lazily
- inline referenced objects internally

The specification does not mandate a particular resolution strategy.

---

## 7.4 Cyclic References

Implementations SHOULD guard against cyclic references.

Example:

- Recipe A references Recipe B
- Recipe B references Recipe A

Such cycles may produce infinite recursion.

Applications SHOULD detect and reject invalid cycles.

---

## 7.5 Reference Overlay Behavior

When an object contains both:

- a `$ref` field
- additional local fields

the referenced object SHOULD be resolved first, after which local fields SHOULD override or extend the referenced content.

Example:

```yaml
- $ref: "#/ingredients/flour"
  quantity: 200
  unit: g
```

This mechanism allows reusable object definitions while preserving recipe-specific customization.

Applications MAY choose their own merge strategy for arrays and extension fields.

---

# 8. Extensibility Model

One of the primary goals of OCS is long-term adaptability.

Cooking ecosystems vary significantly across domains.

The specification therefore includes a formal extension mechanism.

---

## 8.1 Extension Fields

Extensions allow additional metadata without modifying the core specification.

All extensions MUST begin with:

```yaml
x-
```

Example:

```yaml
x-nutrition:
  calories: 320
```

---

## 8.2 Extension Safety

Implementations MUST ignore unknown extensions.

This guarantees:

- forward compatibility
- vendor interoperability
- ecosystem experimentation

Applications MAY choose to process extensions they recognize.

---

## 8.3 Recommended Extension Categories

Common extension domains include:

- nutrition
- allergens
- pricing
- sourcing
- AI metadata
- educational metadata
- localization
- sustainability

These are recommendations only.

The specification intentionally avoids standardizing extension semantics in version 1.0.0.

---

## 8.4 Additional Values Mechanism

Some enumerations are intentionally open.

Documents MAY define additional values through the `additionalValues` object.

This mechanism allows ecosystems to extend categories while preserving interoperability.

Applications SHOULD preserve unknown values whenever possible.

### 8.4.1 Fixed Fields

| Field                | Type       | Description                                                                                     |
| -------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| recipeCategories     | [`string`] | Defines additional recipe category values that MAY be used in Recipe Objects.                   |
| recipeDifficulties   | [`string`] | Defines additional recipe difficulty values that MAY be used in Difficulty Objects.             |
| ingredientCategories | [`string`] | Defines additional ingredient category values that MAY be used in Ingredient Objects.           |
| tags                 | [`string`] | Defines additional tag values that MAY be referenced throughout the document.                   |
| units                | [`string`] | Defines additional unit values that MAY be used for ingredient measurements.                    |
| techniqueCategories  | [`string`] | Defines additional techniques classification values that MAY be used in Procedure Step Objects. |
| equipmentCategories  | [`string`] | Defines additional equipment values that MAY be used in Equipment Objects.                      |
| annotationTypes      | [`string`] | Defines additional annotation values that MAY be used in Annotation Objects.                    |
| mediaTypes           | [`string`] | Defines additional media values that MAY be used in Media Objects.                              |

### 8.4.2 Additional Object Example

```yaml
recipeCategories:
  - festive-special

ingredientCategories:
  - infusion

tags:
  - family-recipe

units:
  - handful

techniqueCategories:
  - fermentation
```

### 8.4.3 Tag Values

Unlike other recommended enumerations, tags are intentionally fully open.

The specification does not define default tag values.

Authors and applications MAY define any tags appropriate to their domain or culinary context.

The `additionalValues.tags` field exists primarily for discoverability, shared vocabularies, and ecosystem coordination.

# 9. Object Model

The OCS object model defines the reusable building blocks of culinary knowledge.

The core object families are:

- document metadata
- recipes
- ingredients
- techniques
- equipment
- annotations
- sources
- procedures

Unless otherwise stated:

- objects MAY contain extensions
- unknown fields SHOULD be ignored
- references MAY substitute inline objects where allowed

The following sections define the normative structure of each object.

## 9.1. Open Cooking Document

Represents the root container of an Open Cooking Specification document.

The Open Cooking Document defines the overall structure, version information, reusable collections, and recipe definitions contained within a document.

### 9.1.1 Fixed Fields

| Field Name       | Type                                                        | Description                                                |
| ---------------- | ----------------------------------------------------------- | ---------------------------------------------------------- |
| openCooking      | `string`                                                    | **REQUIRED**. Specification version.                       |
| info             | [Information Object](#92-information-object)                | **REQUIRED**. Document metadata.                           |
| additionalValues | [Additional Values Object](#84-additional-values-mechanism) | Additional enumeration values.                             |
| ingredients      | Map[`string`, [Ingredient Object](#94-ingredient-object)]   | Reusable ingredient definitions.                           |
| techniques       | Map[`string`, [Technique Object](#95-technique-object)]     | Reusable technique definitions.                            |
| equipment        | Map[`string`, [Equipment Object](#96-equipment-object)]     | Reusable equipment definitions.                            |
| recipes          | Map[`string`, [Recipe Object](#93-recipe-object)]           | **REQUIRED**. MUST contain at least one recipe definition. |

### 9.1.2 Open Cooking Document Example

Example Open Cooking documents are provided throughout this specification.
Readers seeking a minimal introductory example SHOULD refer to [6.2 Minimal Document Example](#62-minimal-document-example).
Readers seeking a more complete and feature-rich example SHOULD refer to [Appendix A — Complete Example Document](#appendix-a--complete-example-document).

## 9.2 Information Object

Represents descriptive metadata about the Open Cooking document.

The Information Object provides human-readable identification and authorship details for a recipe collection or culinary dataset.

### 9.2.1 Fixed Fields

| Field Name  | Type     | Description                   |
| ----------- | -------- | ----------------------------- |
| title       | `string` | **REQUIRED**. Document title. |
| description | `string` | Document description.         |
| author      | `string` | Document author.              |

### 9.2.2 Information Object Example

```yaml
title: Regional French Recipes
description: Traditional household recipes from Normandy
author: Example Author
```

---

## 9.3 Recipe Object

Represents a complete culinary preparation.

A Recipe Object defines ingredients, procedure steps, metadata, and optional reusable references required to reproduce a dish or preparation.

### 9.3.1 Fixed Fields

| Field Name  | Type                                                                                      | Description                                                                        |
| ----------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| name        | `string`                                                                                  | **REQUIRED**. Recipe name.                                                         |
| version     | `string`                                                                                  | Recipe-specific revision identifier.                                               |
| category    | [`string`]                                                                                | Recipe classifications.                                                            |
| tags        | [`string`]                                                                                | Freeform recipe tags.                                                              |
| summary     | `string`                                                                                  | Recipe description.                                                                |
| details     | [Recipe Details Object](#910-recipe-details-object)                                       | Recipe execution metadata.                                                         |
| difficulty  | [Difficulty Object](#911-difficulty-object)                                               | Author-defined recipe difficulty.                                                  |
| ingredients | [[Ingredient Object](#94-ingredient-object) \| [Reference Object](#912-reference-object)] | **REQUIRED**. MUST contain at least one ingredient.                                |
| equipment   | [[Equipment Object](#96-equipment-object) \| [Reference Object](#912-reference-object)]   | Recipe equipment.                                                                  |
| steps       | [[Procedure Step Object](#99-procedure-step-object)]                                      | **REQUIRED**. Ordered preparation steps. MUST contain at least one procedure step. |
| source      | [Source Object](#98-source-object)                                                        | Recipe provenance information.                                                     |
| annotations | [[Annotation Object](#97-annotation-object)]                                              | Supplementary recipe notes.                                                        |
| media       | [[Media Object](#913-media-object)]                                                       | Associated media assets.                                                           |

### 9.3.2 Recipe Object Example

```yaml
name: Tomato Soup
summary: Simple tomato soup with fresh tomatoes.

category:
  - soup

details:
  yield: 4 servings
  prep_time: PT10M
  cook_time: PT30M

ingredients:
  - name: Tomatoes
    quantity: 800
    unit: g

steps:
  - instruction: Simmer tomatoes until soft.
```

---

## 9.4 Ingredient Object

Represents a recipe ingredient or reusable ingredient definition.

Ingredient Objects may describe standalone ingredients, grouped preparation components, or references to reusable sub-recipes.

### 9.4.1 Fixed Fields

| Field Name  | Type                                         | Description                               |
| ----------- | -------------------------------------------- | ----------------------------------------- |
| name        | `string`                                     | Ingredient name.                          |
| category    | `string`                                     | Ingredient classification.                |
| quantity    | `number`                                     | Ingredient quantity. MAY be fractional.   |
| unit        | `string`                                     | Ingredient measurement unit.              |
| recipe      | [Reference Object](#912-reference-object)    | Referenced subrecipe preparation.         |
| annotations | [[Annotation Object](#97-annotation-object)] | Ingredient notes or preparation guidance. |
| media       | [[Media Object](#913-media-object)]          | Associated ingredient media assets.       |

An Ingredient Object MUST define at least one of:

- `name`
- `recipe`
- `$ref`

The fields `recipe` and `$ref` MUST NOT be used together.

The `recipe` field represents a recipe-used-as-an-ingredient,
while `$ref` represents structural object reuse or overlay behavior.

This allows both inline ingredients and reference overlays.

### 9.4.2 Ingredient Object Example

```yaml
name: Flour
quantity: 250
unit: g
category: base
```

#### Ingredient Object Example With Overlay Reference

```yaml
$ref: "#/ingredients/pizza-dough"
quantity: 1
unit: portion
annotations:
  - text: Thaw before use
```

---

## 9.5 Technique Object

Represents a reusable culinary technique or preparation method.

Technique Objects are intended to document repeatable cooking knowledge independently from individual recipes.

### 9.5.1 Fixed Fields

| Field Name  | Type                                         | Description                          |
| ----------- | -------------------------------------------- | ------------------------------------ |
| name        | `string`                                     | **REQUIRED**. Technique name.        |
| category    | `string`                                     | Technique classification.            |
| summary     | `string`                                     | Short technique summary.             |
| description | `string`                                     | Detailed technique explanation.      |
| related     | [`string`]                                   | Related technique names or concepts. |
| annotations | [[Annotation Object](#97-annotation-object)] | Supplementary technique notes.       |
| media       | [[Media Object](#913-media-object)]          | Associated technique media assets.   |

### 9.5.2 Technique Object Example

```yaml
name: Folding
category: mixing
summary: Gently combine ingredients without deflating air.
```

---

## 9.6 Equipment Object

Represents a kitchen tool, appliance, or cooking device used during recipe preparation.

Equipment Objects help describe operational requirements and reusable kitchen resources.

### 9.6.1 Fixed Fields

| Field Name  | Type                                         | Description                                             |
| ----------- | -------------------------------------------- | ------------------------------------------------------- |
| name        | `string`                                     | **REQUIRED**. Equipment name.                           |
| category    | `string`                                     | Equipment classification.                               |
| description | `string`                                     | Equipment description.                                  |
| uses        | [`string`]                                   | Common preparation tasks associated with the equipment. |
| annotations | [[Annotation Object](#97-annotation-object)] | Supplementary equipment notes.                          |
| media       | [[Media Object](#913-media-object)]          | Associated equipment media assets.                      |

```yaml
name: Cast Iron Pan

description: Heavy pan suitable for high heat cooking.
```

### 9.9.1 Fixed Fields

## 9.10 Recipe Details Object

### 9.10.1 Fixed Fields

| Field Name  | Type                                         | Description                         |

# 10. Core Enumerations

OCS defines several recommended enumerations.

These values are:

- intentionally non-exhaustive
- implementation friendly
- extensible

The specification does not attempt to define universal culinary taxonomies.

Applications MAY extend these enumerations using the Additional Values mechanism.

---

## 10.1 Why Enumerations Are Open

Cooking terminology varies globally.

For example:

- one culture may classify a dish as a snack
- another may classify the same dish as street food
- professional kitchens may use internal terminology

Rigid enumerations would reduce interoperability rather than improve it.

The specification therefore provides recommended defaults instead of exhaustive standards.

---

## 10.2 Recommended Usage

Applications SHOULD:

- prefer standardized values when available
- preserve unknown values
- avoid silently rewriting custom values

This encourages ecosystem compatibility.

---

## 10.3 Default Specification Enumerations

The following enumeration values are defined directly by the Open Cooking Specification.

These values are considered part of the default OCS vocabulary.

Implementations SHOULD recognize and support these values without requiring them to be declared in `additionalValues`.

Authors SHOULD prefer these values whenever appropriate in order to maximize interoperability between applications.

Documents MAY still introduce additional custom values through the Additional Values mechanism.

# 11. Validation and Conformance

Conformance defines how closely an implementation follows the specification.

---

## 11.1 Minimal Conformance

A minimally conformant implementation MUST support:

- recipes
- ingredients
- procedure steps

This allows extremely lightweight implementations.

---

## 11.2 Extended Conformance

Extended implementations MAY additionally support:

- references
- annotations
- reusable collections
- techniques
- equipment
- extensions

---

## 11.3 Validation Expectations

Implementations SHOULD validate:

- required fields
- malformed references
- invalid data types
- structurally invalid documents

Implementations MAY additionally validate:

- duplicate identifiers
- enumeration values
- semantic consistency

---

## 11.4 Error Handling

Applications SHOULD provide useful validation errors whenever possible.

Examples:

- missing required field
- invalid duration format
- unresolved reference
- cyclic dependency

Human-readable error reporting is strongly encouraged.

---

# 12. Compatibility Rules

Compatibility rules exist to preserve document longevity.

Recipes often remain useful for decades.

The specification therefore prioritizes stability.

---

## 12.1 Backward Compatibility

Minor versions MUST remain backward compatible.

A document written for:

```text
1.1.x
```

SHOULD remain processable by systems supporting:

```text
1.2.x
```

unless explicitly documented otherwise.

---

## 12.2 Breaking Changes

Breaking structural changes require a major version increment.

Examples include:

- removing fields
- changing field semantics
- changing object structure incompatibly

---

## 12.3 Deprecated Fields

Deprecated fields SHOULD remain supported for at least one minor version before removal.

Implementations SHOULD warn rather than fail when encountering deprecated structures.

---

## 12.4 Unknown Data

Implementations SHOULD ignore:

- unknown fields
- unknown extensions
- unknown enumeration values

unless explicitly prohibited.

This rule is essential for ecosystem evolution.

---

# 13. Security Considerations

Although OCS primarily represents recipe data, implementations may still process untrusted input.

Applications SHOULD guard against:

- malformed references
- cyclic references
- excessively large documents
- malicious extension payloads
- recursive expansion attacks

Implementations resolving external resources SHOULD:

- validate remote content
- restrict unsafe protocols
- apply sandboxing where appropriate

The specification itself does not require network access.

---

# 14. Versioning Policy

The `openCooking` field identifies the specification version used by a document.

Example:

```yaml
openCooking: 1.0.0
```

The specification follows Semantic Versioning.

---

## 14.1 Major Versions

Major versions indicate breaking structural changes.

---

## 14.2 Minor Versions

Minor versions indicate backward compatible additions.

Examples:

- new optional fields
- new object types
- clarification of behavior

---

## 14.3 Patch Versions

Patch releases indicate:

- editorial corrections
- wording clarifications
- non-structural fixes

Patch releases MUST NOT introduce structural incompatibility.

---

# 15. Design Rationale

This section explains why certain architectural choices were made.

---

## 15.1 Structured Ingredients

Ingredient grouping improves readability for complex recipes.

Example groups include:

- batter
- filling
- garnish
- marinade

This avoids ambiguity and improves rendering possibilities.

---

## 15.2 Author-defined Difficulty

Difficulty is intentionally subjective.

Cooking difficulty depends on:

- experience
- equipment
- environment
- culinary background

The specification therefore models difficulty as author-provided guidance rather than objective measurement.

---

## 15.3 Open Enumerations

Culinary language is culturally diverse.

Rigid enumerations would create artificial limitations.

Open enumerations preserve flexibility while still encouraging interoperability.

---

## 15.4 Reference-based Composition

Many recipes are inherently modular.

A sauce may itself contain:

- sub-recipes
- reusable stocks
- reusable spice blends

References reduce duplication and support maintainable recipe collections.

---

## 15.5 Extension Isolation

The `x-` extension model isolates experimental or domain-specific metadata from the stable core specification.

This avoids fragmentation while enabling innovation.

---

# 16. Best Practices

This section provides non-normative implementation guidance.

---

## 16.1 Identifier Naming

Recommended practices:

- use kebab-case identifiers
- keep identifiers stable
- avoid spaces in reusable keys

Example:

```yaml
recipes:
  chicken-stock:
```

---

## 16.2 Writing Procedures

Procedure instructions SHOULD:

- remain concise
- describe one action at a time
- avoid unnecessary ambiguity

Preferred:

```text
Whisk eggs until smooth.
```

Less preferred:

```text
Do the egg thing.
```

---

## 16.3 Ingredient Quantities

Applications SHOULD preserve author intent.

Some recipes intentionally use:

- approximate quantities
- contextual measurements
- culturally specific units

Strict normalization is discouraged unless explicitly required.

---

## 16.4 Human-centered Authoring

OCS documents are expected to be manually editable.

Authors SHOULD prioritize:

- readability
- consistency
- clarity

over extreme normalization.

---

## 16.5 YAML Recommendations

YAML is recommended for:

- educational material
- hand-authored collections
- collaborative editing

JSON may be preferable for:

- APIs
- machine pipelines
- automated tooling

---

# Appendix A — Complete Example Document

The complete example document demonstrates:

- reusable references
- annotations
- equipment
- techniques
- extensions
- additional enumeration values

The example intentionally combines both simple and advanced features in a single document.

```yaml
openCooking: 1.0.0

info:
  title: Advanced Open Cooking Example
  description: Demonstrates reusable references and advanced features
  author: Open Cooking Contributors

additionalValues:
  recipeCategories:
    - street-food

  recipeDifficulties:
    - expert

  tags:
    - family-style

  techniqueCategories:
    - charring

  equipmentCategories:
    - outdoor-cooking

  annotationTypes:
    - chef-note

  mediaTypes:
    - infographic

ingredients:
  flatbread:
    name: Flatbread
    category: bread

  yogurt-sauce:
    name: Yogurt Sauce
    recipe:
      $ref: "#/recipes/basic-yogurt-sauce"

equipment:
  cast-iron-pan:
    name: Cast Iron Pan
    category: cookware

  whisk:
    name: Whisk
    category: utensil

techniques:
  deglazing:
    name: Deglazing
    category: sauce
    summary: Release browned fond using liquid.

  grilling:
    name: Grilling
    category: grilling
    summary: Cook food using direct radiant heat.

  mixing:
    name: Mixing
    category: mixing
    summary: Combine ingredients evenly.

recipes:
  basic-yogurt-sauce:
    name: Basic Yogurt Sauce
    summary: Simple cold yogurt sauce suitable for wraps and grilled dishes.

    category:
      - sauce

    details:
      yield: 250 ml
      prep_time: PT5M

    difficulty:
      value: easy

    ingredients:
      - name: Yogurt
        quantity: 200
        unit: g

      - name: Lemon Juice
        quantity: 1
        unit: tbsp

    steps:
      - name: Combine Ingredients
        instruction: Mix all ingredients until smooth.

        duration: PT2M

        techniques:
          - $ref: "#/techniques/mixing"

  chicken-wrap:
    name: Grilled Chicken Wrap
    summary: Grilled chicken wrapped in flatbread with yogurt sauce.

    version: 1.2

    category:
      - main-course
      - street-food

    tags:
      - quick-meal
      - family-style

    details:
      yield: 4 servings
      prep_time: PT25M
      cook_time: PT20M
      total_time: PT45M

    difficulty:
      value: medium
      rationale: Multiple components are prepared simultaneously.

    ingredients:
      - name: Chicken Thigh
        category: protein
        quantity: 600
        unit: g

        annotations:
          - type: tip
            text: Boneless chicken is easier to slice.

      - $ref: "#/ingredients/flatbread"
        quantity: 4
        unit: unit

      - name: Yogurt Sauce
        recipe:
          $ref: "#/recipes/basic-yogurt-sauce"

      - name: Paprika
        quantity: 1
        unit: tbsp

    equipment:
      - $ref: "#/equipment/cast-iron-pan"

      - $ref: "#/equipment/whisk"

    steps:
      - name: Season Chicken
        instruction: Season chicken with paprika and salt.

        duration: PT5M

      - name: Grill Chicken
        instruction: Grill chicken until fully cooked.

        duration: PT20M

        techniques:
          - $ref: "#/techniques/grilling"

        annotations:
          - type: warning
            text: Internal temperature should reach safe cooking levels.

      - name: Warm Flatbread
        instruction: Warm flatbread before assembly.

        duration: PT2M

      - name: Assemble Wraps
        instruction: Assemble wraps and serve immediately.

        duration: PT5M

    source:
      name: Family Recipe Notebook
      summary: Adapted household recipe.

    media:
      - type: image
        url: https://example.org/images/chicken-wrap.jpg
        caption: Finished grilled chicken wrap

      - type: video
        url: https://example.org/videos/chicken-wrap.mp4
        caption: Wrap assembly demonstration

    x-nutrition:
      calories_per_serving: 540

    x-allergens:
      - dairy
      - gluten
```

# Final Notes

The Open Cooking Specification is intentionally designed as a practical interoperability layer rather than a rigid culinary authority.

Its purpose is to provide a common language for representing recipes while remaining flexible enough to support:

- personal cooking notes
- professional applications
- educational systems
- collaborative archives
- AI-assisted culinary tools

The specification is expected to evolve incrementally over time while preserving readability, portability, and long-term compatibility.
